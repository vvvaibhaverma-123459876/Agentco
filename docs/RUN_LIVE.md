# Running AgentCo live (local Docker Compose)

The complete product — backend API, all three workers, frontend, PostgreSQL,
Kafka — on one machine with one command. This is the first supported way to run
AgentCo as a whole system rather than as a test suite.

## Quick start

```bash
make live-up      # generates .env.live (first run), builds images, boots everything
make live-logs    # watch it come up (migrations + seed run inside the backend container)
make live-smoke   # end-to-end verification of the running stack
```

Then open **http://localhost:3000** (dashboard) — API at **http://localhost:3001**.

Stopping:

```bash
make live-down     # stop containers, keep data
make live-destroy  # stop AND delete the database volume
```

## What boots, in order

| Service | Image | Role |
|---|---|---|
| `postgres` | postgres:16-alpine | The only hard runtime dependency. Host port 127.0.0.1:5442. |
| `zookeeper` + `kafka` | confluentinc 7.6.1 | Event delivery (production readiness requires Kafka). Internal only. |
| `backend` | `deploy/local/Dockerfile.runtime` | Applies all migrations, runs the bootstrap seed, then serves on 127.0.0.1:3001. |
| `outbox-worker` | same image | Relays the transactional outbox to Kafka. |
| `civilization-scheduler` | same image | The civilization's heartbeat (orchestration ticks). |
| `task-worker` | same image | Executes durable tasks by spawning the Python executor. |
| `frontend` | `frontend/Dockerfile` | Next.js dashboard on 127.0.0.1:3000, proxying to the backend. |

The runtime image is Node 20 **plus Python 3.13** with `agents/`, `runtime/`,
`calibration/`, `autonomy/`, and `scripts/` laid out at `/app` — the backend
spawns Python subprocesses at runtime (specialist agents, durable-task
executor), and the compiled path resolution requires the backend package at
`/app/backend`. The plain `backend/Dockerfile` (Node-only) cannot run these
paths; it remains for the k8s CI audit.

## Boot-time self-provisioning

The backend container entrypoint (`deploy/local/backend-entrypoint.sh`) does
three things no other part of the repo did before:

1. `node dist/db/migrate.js` — applies all migrations (the compiled runner;
   `npm run db:migrate` needs ts-node, which production images prune).
2. `node dist/cli/seed-live.js --emit-env` — idempotently ensures the
   civilization root, an `agentco-llm-budget-authority` service actor, its
   funded `llm_tokens` account, and exports `LLM_RESOURCE_ACTOR_ID` /
   `LLM_RESOURCE_ACCOUNT_ID` — which production boot **requires** when LLM
   credentials are set, but which nothing previously created. The IDs are also
   written to a shared volume for the worker containers.
3. `exec node dist/server.js`.

## Configuration (.env.live)

Generated by `make live-init` (`scripts/live/generate_env.sh`), never
committed. Every secret is a fresh `openssl rand`; the Postgres password is
random so the production gate's dev-password check passes honestly.

**LLM provider.** By default the stack points at an Ollama server on the Docker
host (`http://host.docker.internal:11434/v1`, model `qwen2.5:7b`):

```bash
brew install ollama && ollama pull qwen2.5:7b   # once
```

To use OpenAI instead, export `OPENAI_API_KEY` before the **first**
`make live-init` (or `bash scripts/live/generate_env.sh --force` to rotate).
The stack boots and serves fine with the LLM endpoint down — agent cognition is
the only thing that degrades; `make live-smoke` reports reachability.

**Vault caveat (honest posture).** Production boot demands `VAULT_ADDR` /
`VAULT_TOKEN`, but no code in the current backend ever opens a Vault
connection — secrets are consumed from env. `.env.live` therefore sets
`VAULT_ADDR` to a deliberately unresolvable `.invalid` hostname: if the
codebase ever grows a real Vault client, it will fail loudly instead of
appearing integrated.

## Security posture — read before exposing anything

Every published port binds to **127.0.0.1 only**, on purpose:

- The frontend has **no human login**, and its server-side proxy attaches the
  privileged `AGENTCO_API_KEY` to every browser request. Anyone who can load
  the page can call the full write API.
- Exposing this stack beyond loopback requires building a human auth layer
  first. Do not port-forward 3000/3001 to a network as-is.

## Verification

`make live-smoke` proves, against the running stack: backend liveness and
readiness (readiness transitively checks Postgres, Kafka, and the
real-provider contract), API auth posture (401 without key / 200 with),
frontend health, the frontend proxy genuinely reaching the backend, a real
write through the public API (actor registration), civilization operator
overview, and LLM endpoint reachability (informational).
